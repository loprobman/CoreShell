GitHub Copilot: ## Packaging metadata (`pkg.json`, docs in the package)

### What it means

Each command should be distributable as a **standalone package** — a small bundle containing:
- `pkg.json`: machine-readable metadata (name, version, description, dependencies)
- `docs/`: generated help text (e.g. `docs/ls.md`) extracted from `print_usage()`

The `pkg.json` would look something like:

```json
{
  "name": "ls",
  "version": "1.0.0",
  "description": "list directory contents",
  "author": "...",
  "docs": "docs/ls.md"
}
```

where `description` comes directly from `cmd_ls_spec.summary`.

---

### Why it's useful

Right now every command is baked into the shell binary. The anatomy allows a future `pkg` command to:

1. **Install** a new command without recompiling the shell
2. **Share** commands between users/machines
3. **Auto-generate docs** — by calling `spec->print_usage()` at build time and capturing the output into `docs/ls.md`, so docs never go stale

The `cmd_spec_t` fields are the single source of truth feeding `pkg.json`:
| `cmd_spec_t` field | → `pkg.json` field |
|---|---|
| `.name` | `"name"` |
| `.summary` | `"description"` |
| `.long_help` | `docs/<name>.md` body |

---

### What's missing in the project today

For each command directory (e.g. cmd_ls) you'd need to add:

1. **`pkg.json`** — written once manually or generated by a `pkg build` subcommand
2. **`docs/ls.md`** — generated by running `ls --help` and capturing output, or calling `ls_print_usage()` from a build script

The C-side infrastructure (`cmd_spec_t`, `print_usage`, `summary`, `long_help`) is **already fully in place** — it's purely the packaging artifacts that are missing.

## Session 3 – Work Report

### What the slides require

The session goal is **"One Binary, Many Commands"** in a **BusyBox-style multicall** architecture. The key pattern from the slides:

```c
// multicall selection
const char *cmd = (argc > 1) ? argv[1] : argv0_basename(argv[0]);
// adjust argv so run() sees the command name as argv[0]
int run_argc = (argc > 1) ? argc - 1 : argc;
char **run_argv = (argc > 1) ? &argv[1] : argv;

const cmd_spec_t *spec = find_command(cmd);
if (!spec) return unknown_command(cmd);
return spec->run(run_argc, run_argv);
```

This means the binary operates in **two modes**:
1. `./CoreShell ls -la` → reads `argv[1]` as the command, skips REPL, dispatches directly
2. `./ls -la` (symlink) → reads `argv[0]` basename as the command, same dispatch

---

### What is missing ❌

#### 1. `main()` doesn't accept `argc`/`argv`

Currently declared as `int main(void)`. Multicall dispatch requires `int main(int argc, char **argv)`.

#### 2. No `argv0_basename()` helper

Needed to extract the command name from a symlinked invocation (ls → `"ls"`). Equivalent to POSIX `basename()` but safe to implement inline.

#### 3. No multicall entry point

The binary has no logic to detect `argv[1]` or `argv[0]` as a direct command dispatch. When called as `./CoreShell ls -la` it currently drops into the REPL and ignores `ls -la`.

#### 4. No `unknown_command()` handler

The slides reference `unknown_command(cmd)` when `find_command()` returns NULL in multicall mode. Currently the REPL falls through to `fork`/`execvp` instead.

#### 5. `fork`/`execvp` fallback still present

The slides explicitly state **"No fork/exec"**. The current `execute_command()` in main.c forks external programs. This should be removed (or guarded behind the REPL path only, depending on interpretation).

#### 6. Dual-mode `main()` logic

`main()` needs to decide at startup:
- If `argc > 1` **and** `argv[1]` matches a known command → multicall mode (no REPL)
- If `argv[0]` basename is not `"CoreShell"` → multicall mode (symlink invocation)
- Otherwise → interactive REPL mode (current behavior)
